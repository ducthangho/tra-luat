WP710: Add a bounded Windows NLM credential refresh and opt-in keepalive with a
real notebook canary, serialized stage, machine-readable failures, and offline
behavioral tests. `nlm-auth-stage`, `secrets-set --nlm` and `secrets-stage` share
one gate: they upload NLM credentials only after a live canary whose raw JSON
answer is exactly one notebook object (every id key equal to the expected id,
every title/name key a non-blank string, no duplicate or case-variant keys, no
`ok:false`/`error`), and read the credential jar only after that canary. The
answer must be standard JSON accepted identically by the Python command and the
PowerShell wrapper: `NaN`/`Infinity`, numbers that overflow a double, lone
escaped surrogates, duplicate keys at any depth and nesting deeper than 64 are
refused on both sides (38 shapes measured in parity, 0 differences).
`--force` cannot bypass the gate, and the wrapper applies the same allow-list. A
payload guard sends `nlm_auth` in a bundle only when it is the jar that just
passed the canary: `secrets-set` without `--nlm` on a bundle that carries
`nlm_auth` is refused (rc 4), `secrets-stage` without a jar stops (rc 3), and
`--no-nlm` removes `nlm_auth` from the packed config. RUNBOOK and the GWS
remediation hints now give the working command for each case (`--nlm` on a
machine with a jar and a positive canary, otherwise `gws-auth-stage` or
`secrets-stage --no-nlm`). The three commands print
only fixed canary codes and exception class names; an exception mid-command
returns rc 5 instead of a traceback (rc 5 does not prove nothing was uploaded).
The canary notebook is pinned by `TL_CANARY_NOTEBOOK_ID`, which a profile config
cannot overwrite. The wrapper marks every child with `TRA_LUAT_NLM_OP`; on Linux
it is also a child subreaper, so it stops and confirms its whole subtree (even
descendants that cleared the marker) on timeout and before the next step, and a
new lock owner waits for any marked process. A process whose environment cannot
be read counts as unknown, not absent. Where the old tree cannot be proven gone
(not Linux, a record without marker, unknown members) the next owner is held in
a bounded quarantine (`tree_quarantine`, rc 5) and released only after
`-UnconfirmedQuarantineSeconds` (default 900) with `takeover=quarantine_elapsed`
in the evidence; a tree proven alive is never released. A version probe that
leaves an unconfirmed tree now stops the run. On Windows descendants cannot be
enumerated at all: a timeout is never confirmed there, and a descendant that
drops the pipes after a successful step is NOT stopped (not measured natively;
needs a Job Object).
`stage_failure` means the stage command was called and may have uploaded.
