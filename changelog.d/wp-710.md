WP710: Add a bounded Windows NLM credential refresh and opt-in keepalive with a
real notebook canary, serialized stage, machine-readable failures, and offline
behavioral tests. `nlm-auth-stage`, `secrets-set --nlm` and `secrets-stage` share
one gate: they upload NLM credentials only after a live canary whose raw JSON
answer is exactly one notebook object (every id key equal to the expected id,
every title/name key a string that is not blank by one explicit 35-character
table kept in both languages, no duplicate or case-variant keys, no
`ok:false`/`error`), and read the credential jar only after that canary. The
answer must be standard JSON: `NaN`/`Infinity`, numbers that overflow a double,
lone escaped surrogates, duplicate keys at any depth and nesting deeper than 64
are refused on both sides. The wrapper reads the canary stdout as bytes and
applies the transformation `nlm_cli._run` applies before the Python command
judges it (UTF-8 with U+FFFD, newline translation, `splitlines`, keyring-noise
lines), so a UTF-8 BOM is refused by both. Measured scope, Linux only (pwsh
7.4.6, Python 3.11): the two reader functions agree on 101 shapes (0
differences; the previous head differed on 8, U+001C-U+001F titles), and the
wrapper and the Python stage gate agree on 168 byte sequences sent through a
real child process stdout (0 differences). Not measured: Windows, the real
`nlm` CLI, other Python versions; no claim is made for inputs outside these
sets.
`--force` cannot bypass the gate, and the wrapper applies the same allow-list. A
payload guard sends `nlm_auth` in a bundle only when it is the jar that just
passed the canary: `secrets-set` without `--nlm` on a bundle that carries
`nlm_auth` is refused (rc 4), `secrets-stage` without a jar stops (rc 3), and
`--no-nlm` removes `nlm_auth` from the packed config. RUNBOOK and the GWS
remediation hints now give the working command for each case (`--nlm` on a
machine with a jar and a positive canary, otherwise `gws-auth-stage` or
`secrets-stage --no-nlm`). The three commands print
only fixed canary codes and exception class names; an exception mid-command
returns rc 5 instead of a traceback (rc 5 does not prove nothing was uploaded).
The canary notebook is pinned by `TL_CANARY_NOTEBOOK_ID`, which a profile config
cannot overwrite. The wrapper marks every child with `TRA_LUAT_NLM_OP`; on Linux
it is also a child subreaper, so it stops and confirms its whole subtree (even
descendants that cleared the marker) on timeout and before the next step, and it
reaps the adopted descendants it stopped (`waitpid`, never the step's direct
child, which .NET waits for): measured over 4 keepalive cycles, 0 zombie
children in every interval (previous head: 1, 2, 3). A new lock owner waits for
any marked process. A process whose environment cannot be read counts as
unknown, not absent. After an owner died on Linux, the record (format 2) also
carries the step start, the step's pipes and the owner's ancestor chain: a
process started during the step that still holds one of those pipes blocks the
takeover, and one that cleared the marker and dropped the pipes is unknown
unless its parent line shows it was not adopted (fail-closed; it can also hold
back an unrelated process started under the same ancestors). Records without
format 2 are still checked by marker only. A Linux tree that is measured and
unknown is quarantined (`tree_quarantine`, rc 5) with NO timer exit: it ends
when the tree is proven gone or by `-OperatorReleaseReason`, which is recorded
in the evidence and never releases a tree proven alive. Only a tree that cannot
be measured at all keeps a timer exit, and only on Linux (a record without
marker): `-UnconfirmedQuarantineSeconds` (default 900) with
`takeover=quarantine_elapsed`; that exit awaits an owner decision. A version probe that
leaves an unconfirmed tree now stops the run.
Windows (g4): every step runs inside its own named Job Object with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The child is created suspended, assigned
to the job, checked to be a member and only then resumed, so its descendants
are born inside the job whether or not they keep the marker or the pipes. The
job's `ActiveProcesses` count is the measurement: after a step (success or
timeout) whatever is still in the job is terminated and the next step starts
only when the count reads 0 (`tree_measurement=windows_job_object`,
`tree_state=gone`). A job that cannot be created, a child that cannot be
placed in it, or a count that does not reach 0 ends the run with rc 5
(`tree_containment`, reason in `containment_reason`) and never falls back to an
uncontained child. The operation record names the job; a later owner opens it:
members left block (`job_alive`, never released by the operator), a count of 0
or no job of that name is a takeover, except that a record whose owner had
already failed to empty its job stays quarantined (`job_closed_unconfirmed`).
"No job of that name" rests on the kill-on-close contract, not on a count.
Off Linux the quarantine timer no longer releases anything
(`-UnconfirmedQuarantineSeconds` has no effect there); the exit is
`-OperatorReleaseReason`. A successful step whose tree can be neither
enumerated nor contained is no longer treated as finished: it keeps its record
and ends the run with rc 5, so a platform that is neither Linux nor Windows
cannot stage. Linux behaviour of the previous head is unchanged.
Measured on Windows 11 (pwsh 7.6.6, Python 3.13.1), offline, fake CLI:
`Tests.ps1` 32 passed, 0 failed, twice (the previous head stops at the first
loop's `stage` case with rc 5 there). 9 mutants on temporary copies, each red
at its target case: assignment removed (membership check answers,
`job_verify_failed`), assignment and membership check removed, count check
removed, unmeasured tree released as before, timer releasing again,
kill-on-close removed, closed-but-unconfirmed job cleared, job with members
let through, job-creation failure ignored. Kill-on-close, 30 rounds with a
two-process job whose only holder is killed: the job name stopped resolving
while a member was still alive 0 times; both members were gone within 34 ms.
One fixture was encoding-dependent on Windows (`print` of U+FEFF dies under a
console code page); it now writes bytes.
Not measured: the real `nlm` CLI and a real browser on Windows; processes
started on the tree's behalf by a broker outside it (WMI, Task Scheduler, an
already running browser) are outside any job; the Linux run of this head's
`Tests.ps1` (case t was rewritten and was run on Windows only).
`stage_failure` means the stage command was called and may have uploaded.
