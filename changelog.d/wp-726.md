WP726: The three NLM shell scripts no longer use `nlm login --check` (which
reports green on a dead session) to decide whether NotebookLM is alive, and no
longer swallow the exit code of `nlm-auth-stage`.
`scripts/nlm-auto-refresh.sh` (run by the maintenance Routine) takes its verdict
from `tl nlm-auth-stage`, which runs the WP710 live canary before reading the jar:
rc 0 alive and bundle refreshed (exit 0), rc 4 canary not positive and nothing
uploaded (exit 3), anything else infrastructure or inconclusive (exit 2, may have
written partially). `scripts/env-reimport.sh` and `scripts/nlm-auth-import.sh`
probe with the same body-checking canary as the stage gate
(`_nlm_auth_alive(..., require_notebook_body=True)`) and only use its exit code:
env-reimport exits 3 when dead and the new 4 when inconclusive; nlm-auth-import
keeps exit 4 (dead, old jar restored), adds 6 (inconclusive, new jar kept, no
stage) and now exits 5 when the stage fails, telling rc 4 (canary refused, no
upload) apart from other failures, instead of reporting "cookie still usable"
and exiting 0. As a consequence nlm-auto-refresh keeps the plaintext export on
Drive when import+stage did not both succeed, which its own comment already
required, and after a successful import it no longer stages a second time.
env-reimport reports a failing `nlm-auth-load` by exit code only (it used to
print the first line of the command output, which can carry a raw download
error), and the nlm-auth-import header documents exit codes 5 and 6. Recovery hints point to the WP710 wrapper on the host holding the
original browser profile. The canary, stage and load steps
are reported by exit code only (their output may carry cookies); other steps
of these scripts were not audited for that.
Fragment `wp726_script_nlm_canary` runs the real scripts under bash against a
stateful fake root where `nlm login --check` always says valid; it checks exit
codes, stage call counts (including the fresh-export path), plaintext deletion,
zero `login --check` calls and no leaked sentinel (including a failing load).
It finds bash only through `ops/bash_nen.py::tim_bash()`.
On a non-POSIX host, or a tree without `ops/bash_nen.py` (release bundle), the
fragment returns true after printing a skip line: the fragment API has no
`skipped` state (declared deviation from spec N6, open for the owner).
The maintenance Routine configuration was not touched; its reaction to the new
exit codes is not measured.
