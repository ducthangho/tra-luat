WP831: the Linux and macOS `rg` recipes in `ops/cong_cu.yaml` now pick their folder the same way the Windows one
does. After `apt-get`/`brew` they print the first folder whose `rg` exists, is executable and passes
`ops/cong_cu.py kiem-tra --chi rg`. Linux tries `/usr/bin`, then `command -v rg`. macOS tries `$(brew --prefix)/bin`,
then `command -v rg`. Before, both printed `dirname "$(command -v rg)"`, so a broken `rg` earlier in PATH was the folder
handed back. When no candidate passes, the install now fails instead of handing back a folder. The chosen folder goes
to `$GITHUB_PATH` only when the bare `rg` still fails the check: writing `/usr/bin` unconditionally put the system
`python` ahead of setup-python's in later CI steps. `CONG_CU_GOC` (empty by default) prefixes the Linux `/usr/bin`
candidate so tests can isolate it. `docs/GOI_AGENT_DA_NEN.md` now lists the required tools per platform, as
`_bat_buoc` in `launcher.py` resolves them, and says that exit 12 also covers `BI_CHE` (the bare-name `rg`/`git` is
broken while another copy runs). New `r831_*` cases and five `wp831_*` YAML mutations; the `wp802` Windows anchor is
longer so that it still matches exactly once. The package-size ratchet in `r291_docs_ngoai_goi` and
`r357_agents_ngoai_goi` moves from 187 to 189 files (`changelog.d/wp-802.md`, which #802 landed without regenerating
the manifest, and `changelog.d/wp-831.md`).
`ops/cai_cong_cu.sh` now pins the Python it picked (`python`, `python3` or `py -3`) to its absolute path before any
recipe runs: the `rg` recipes prepend the candidate folder to PATH, and a bare `python` there could resolve to a
different interpreter without PyYAML, rejecting a working `rg`. Under `--bat-buoc`, each tool's run is sourced in
the same shell after the previous tool changed PATH, so those runs now reuse the parent's pinned Python (marked by
a non-exported `CAI_CONG_CU_PY_CUA=$$`) instead of picking again.
