WP858: `ops/cai_cong_cu.sh` gains `chon_thu_muc_chay_duoc [--win] <tool> <candidates>...`, and the twelve `git`,
`python`, `shellcheck` and `bash` recipes in `ops/cong_cu.yaml` call it instead of printing
`dirname "$(command -v <tool>)"`. Before, a broken copy earlier in PATH was the folder handed back. The function
prints the first candidate folder that makes `ops/cong_cu.py kiem-tra --chi <tool>` pass when put first in PATH, run by
the already-pinned absolute Python. There is no separate file-exists or executable check: the checker decides.
Candidates: Linux `/usr/bin` (prefixed by `CONG_CU_GOC` in tests), macOS
`$(brew --prefix)/bin`, Windows the folders choco installs into (`Git/cmd`, `Git/bin`, `Git/usr/bin`, `chocolatey/bin`,
`C:/Python3*`), then `command -v`. No passing candidate fails the install, and so does a failing `cygpath` or a
failed write to `$GITHUB_PATH`: the function returns 1 itself, because `errexit` is off inside `$(eval ...)`. When the
bare name already passes, it leaves PATH and `$GITHUB_PATH` alone and prints `:giu-nguyen-PATH:`, which is not a
folder, as its last line. Re-printing that folder used to put it first in PATH again, so under `--bat-buoc` the `bash`
recipe brought back a broken `rg` from the same folder and the final `rg` check failed (Codex, #831 round 4); printing
nothing would let the installer's own last output line be taken as the folder. On Windows candidates go through
`cygpath -u` and `$GITHUB_PATH` gets `cygpath -w` of the folder. `rg` keeps its own selector.

`python` first in PATH is still not detected (`python-probe-khong-theo-PATH`).
