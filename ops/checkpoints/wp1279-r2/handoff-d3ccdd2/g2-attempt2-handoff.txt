**Causes and fixes**
- **X3-02:** a false positive. The check searched the raw module text, and the only match was the module's header comment saying it does no `Get-PSSession` adoption. The module only calls `New-PSSession`, `Remove-PSSession` and `Invoke-Command`, all fully qualified.
  - The static check now uses the PowerShell parser and scans every non-comment token, including strings and module-qualified names, for `Get-PSSession`, `Connect-PSSession` and `Enter-PSSession`.
  - A guard fails the case with `TOKEN_SCAN_VACUOUS` if the scan cannot see `New-PSSession`, so it can't pass by scanning nothing.
  - New behavioural check: recording global stand-ins for the three commands are installed while `status` without `connect` runs through both `px` and the in-process `Run-Px.ps1`. Both must fail with `NotConnected` and record zero calls (`AUTOCONNECT[...]` otherwise). The stand-ins are removed in `finally`.
  - The fresh-process-disconnected and module-conflict child checks are unchanged.
- **X5-03:** the loop variable `$s` shadowed the scratch root `$S`. PowerShell resolves names through the caller's scopes, ignoring case. That turned the junction target into a relative path, and it also quietly broke every tree snapshot inside the loop. Renamed to `$sub`. All subcases are unchanged: the seven pending/unknown/malformed/unreadable variants, junction → `PendingGuardUnverified`, `Force` override, and settled journal.
- **X5-05:** the local `$sha` replaced the shared SHA256 hasher `$Sha` for later helper calls. Renamed to `$occSha`. The junction setup and the checks now sit in `try`/`finally`, and the `finally` deletes only the junctions actually created. This tail of the case (collision handling and junction cleanup) never ran natively before.
- **X6-02:** the snapshot `$keep` shadowed `$Keep`, and the snapshot `$repo` shadowed `$Repo`.
  - So every WhatIf call ran with a snapshot string as `RepositoryRoot` and failed validation. The zero-effects check was measuring nothing, and the junction probe then failed with "illegal path".
  - The snapshots are renamed. A new `WHATIF_MATRIX_VACUOUS` check requires at least 10 actual dry runs out of the 30 calls; reading the module, I expect about 23.
- **The same bug elsewhere:** a new setup check, `Find-ScopeShadowing`, parses the harness and refuses to run if any inner variable (assignment, `foreach` variable or parameter) reuses a top-level name. It first runs on a small sample containing the two original bug shapes and must flag exactly those.
  - To make the harness pass its own check, I also renamed `$s` in `Get-Bound` and the X5-07 "two services" handler, and five top-level names: `$p`, `$g`/`$gl`, `$d`, `$b`, `$m` and `$rc`. None of these were live bugs.
  - It does not catch one helper's local shadowing another helper's local. I checked those by hand (`Invoke-Guarded` against the variables its callers' calls use); none collide.
